Student stories (STU)
STU-01
Launch activity from Canvas  ★
STUDENT
Phase 2 — Pilot
Story
As a student, I want to launch my learning activity directly from a Canvas assignment into the Student App so that I do not need a separate login or URL.
Acceptance
✓  Clicking the Canvas assignment link initiates an LTI 1.3 launch into the Student App without prompting for credentials.

✓  The orchestrator assigns an ephemeral temporary identity (tempuser) and acquires a SAP sandbox account from the pool invisibly — the student never sees either.

✓  The student is routed to the correct wizard phase: the start of the learning activity for a new session, or the last reached phase for a resumable session.

✓  If the SAP account pool is exhausted, a clear, non-technical error message is displayed with an instruction to try again shortly.

✓  No student PII is stored on the platform during or after the launch process.

STU-02
Complete check-in survey
STUDENT
Phase 1 — PoC
Story
As a student, I want to answer a short set of questions about my background so that the subsequent conversation is relevant to my level of experience.
Acceptance
✓  The check-in presents 3–4 questions generated by the AI from the module's domain context.

✓  Questions use appropriate response formats: Likert scale, multiple choice, or short text (max 150 chars).

✓  All questions must be answered before the student can advance to the evaluation conversation.

✓  Check-in responses are not graded — no feedback is shown to the student at this stage.

✓  Check-in responses are stored de-identified in Aurora for research purposes after the session completes.

STU-03
Work through the learning activity  ★
STUDENT
Phase 2 — Pilot
Story
As a student, I want to see all the content I need — background reading, step-by-step instructions, and SAP tasks — in a clear, structured sequence so that I know what to do and in what order.
Acceptance
✓  The learning activity displays content blocks in the author-defined sequence: conceptual blocks (reading, short video), instructional blocks (numbered steps), and SAP activity blocks.

✓  Conceptual blocks are displayed and marked complete when the student scrolls through or self-reports completion.

✓  Instructional blocks display numbered steps with descriptions; understanding notes are not shown to students.

✓  SAP activity blocks display the task prompt and a link or path to the SAP sandbox.

✓  Gate blocks must be completed before the next block in the sequence is unlocked; a clear visual indicator shows which blocks are locked, active, and complete.

STU-04
Work with instructions and SAP side by side  ★
STUDENT
Phase 2 — Pilot
Story
As a student, I want to view my step-by-step instructions and the SAP environment at the same time, in a layout that suits my screen, so that I can work back and forth without losing my place.
Acceptance
✓  When an instructional block and a SAP activity block are grouped as a concurrent pair, the student can choose between a side-by-side layout (screens ≥ 1200px) and a modal or tabbed layout (screens 768px–1199px).

✓  The student can switch layouts at any time without losing progress in either panel.

✓  The student can freely move between reading instructions and working in SAP in any order — no step-by-step lockstep is enforced within the pair.

✓  The chosen layout preference is remembered for the duration of the session.

✓  On screens below 768px, the app displays a message that this activity requires a larger screen.

STU-05
Proceed to assessment after SAP completion  ★
STUDENT
Phase 2 — Pilot
Story
As a student, I want the system to confirm my SAP work is complete before the assessment conversation begins so that I know my activity has been recognized.
Acceptance
✓  The "I have completed the activity" button is only available after all gate blocks in the learning activity have been completed.

✓  After submitting, a visual indicator shows that SAP verification is in progress.

✓  If all required SAP documents are found, the student is automatically advanced to the check-in survey and then the checkout conversation.

✓  If documents are missing, a message lists which document types were not found and invites the student to complete them.

✓  If SAP is temporarily unavailable, a user-facing message explains the issue without technical detail and invites a retry in a few minutes.

✓  Verification polling occurs at 3-second intervals and times out after 15 seconds with an appropriate message.

STU-06
Engage in checkout conversation
STUDENT
Phase 1 — PoC
Story
As a student, I want to have a supportive conversation about what I did and learned so that I can demonstrate my understanding in my own words rather than through a quiz.
Acceptance
✓  The conversation opens with an acknowledgment of the completed activity and a reference to the student's check-in answers.

✓  The agent asks one question at a time and waits for a response before continuing.

✓  The agent probes vague or incomplete answers with a follow-up rather than accepting them without engagement.

✓  The agent never uses the words "correct" or "incorrect."

✓  The agent validates effort before redirecting: e.g. "That's a good start — let's go a bit deeper."

✓  The conversation includes at least one question about how the skills connect to the student's future career.

✓  A typing indicator is shown while the AI response is loading.

✓  The conversation concludes with the agent providing one observation of strength and one area for development.

STU-07
Receive summary evaluation
STUDENT
Phase 1 — PoC
Story
As a student, I want to see a clear, honest evaluation of my conversation so that I understand what I demonstrated well and what I should continue to develop.
Acceptance
✓  The summary displays a rating for each rubric dimension: Strong, Developing, or Needs further work.

✓  Each dimension rating is accompanied by a 2–3 sentence narrative referencing specific things the student said.

✓  A per-learning-outcome status (achieved / partial / not addressed) is displayed.

✓  An overall summary of 3–5 sentences is displayed, including one strength and one development area.

✓  If a badge was awarded, it is displayed prominently with a link to the student's Credly profile.

✓  If the assessment threshold was not met, a clear but encouraging message explains this and offers the retry option.

✓  The evaluation can be printed by the student from the browser.

STU-08
Retry the checkout conversation
STUDENT
Phase 2 — Pilot
Story
As a student, I want the option to retry the assessment conversation if I did not meet the threshold so that I have a fair opportunity to demonstrate my understanding.
Acceptance
✓  The retry option is offered on the summary screen when one or more dimensions are rated "Needs further work."

✓  A retry does not require the student to repeat the check-in survey or the SAP activity.

✓  The retry conversation is focused on the dimensions that were rated as needing further work.

✓  The student is informed of the maximum number of attempts remaining before beginning a retry.

✓  If the retry limit has been reached, a message advises the student to contact their instructor.

STU-09
Resume an interrupted session  ★
STUDENT
Phase 2 — Pilot
Story
As a student, I want to be able to resume my activity if my session is interrupted so that I do not lose my progress.
Acceptance
✓  Relaunching the Canvas assignment within the 8-hour session window resumes the student at their last completed phase.

✓  Content block completion state, check-in responses, and conversation history are restored on resume.

✓  A brief message informs the student that their session has been resumed.

✓  If the DynamoDB session record has expired (TTL elapsed, default 8 hours), the student is informed and a new session begins from the start of the learning activity.

✓  No session state is stored in the student's browser (no localStorage or sessionStorage). Resume works by relaunching from Canvas.

✓  No student PII is held in Aurora — the resume lookup uses the Canvas UUID server-side only.


Domain expert stories (AUT)
AUT-01
Create a new instructional recipe  ★
DOMAIN EXPERT
Phase 1 — PoC
Story
As a domain expert, I want to create a structured recipe for my learning module in the Admin App so that the system can deliver a complete, domain-specific learning and assessment experience without code changes.
Acceptance
✓  The Admin App authoring module presents all recipe sections in clearly labeled form panels.

✓  Required fields (module title, description, learning outcomes, key concepts, rubric dimensions) are marked and validated before saving.

✓  Saving the recipe creates a new versioned record in Aurora and sets it as the active version.

✓  The saved recipe is immediately available for new student sessions launched against that module from Canvas.

✓  A confirmation is shown on save with the version number and timestamp.

AUT-02
Author content blocks and learning sequence  ★
DOMAIN EXPERT
Phase 2 — Pilot
Story
As a domain expert, I want to define the learning activity as an ordered sequence of content blocks — conceptual, instructional, and SAP — so that students receive the right content in the right order.
Acceptance
✓  The authoring form allows adding three types of content blocks: conceptual (reading or short video), instructional (numbered steps), and SAP activity (task prompt).

✓  Blocks can be added, reordered, and deleted before saving.

✓  Any block can be marked as a gate, requiring it to be completed before the next block unlocks.

✓  SAP activity blocks are always gates and are automatically flagged as such.

✓  The block sequence is displayed visually, showing which blocks are gates and which are flexible.

AUT-03
Group blocks as concurrent pairs  ★
DOMAIN EXPERT
Phase 2 — Pilot
Story
As a domain expert, I want to group an instructional block and a SAP activity block as a concurrent pair so that students can view them side by side or in a modal while working.
Acceptance
✓  The authoring form allows pairing one instructional block with one SAP activity block into a concurrent pair.

✓  A concurrent pair is displayed to the student with layout options (side-by-side or modal/tabbed).

✓  A pair counts as a single position in the block sequence — it is completed when the SAP activity within it is verified.

✓  The author can dissolve a pair and return the blocks to independent sequence positions.

✓  A tooltip explains to the author what a concurrent pair means for the student experience.

AUT-04
Define numbered activity steps within instructional blocks  ★
DOMAIN EXPERT
Phase 1 — PoC
Story
As a domain expert, I want to describe the SAP activity as numbered steps within an instructional block so that students have clear guidance and the AI agent has specific context for probing.
Acceptance
✓  Steps within an instructional block are entered in sequence and auto-numbered.

✓  Each step has a required description and two optional fields: outcome tag(s) and understanding note.

✓  Steps can be added, reordered, and deleted within the block.

✓  A step with all three fields is visually distinguished as probe-eligible; a step with description only is shown as context-only.

✓  A step coverage summary shows which learning outcomes have at least one tagged step, prompting the author to address gaps.

AUT-05
Map activity steps to learning outcomes  ★
DOMAIN EXPERT
Phase 1 — PoC
Story
As a domain expert, I want to tag each instructional step with one or more learning outcomes so that the AI agent knows which outcomes each step develops.
Acceptance
✓  Outcome tags are selected from the numbered list of learning outcomes defined in the recipe.

✓  Multiple outcomes can be tagged per step.

✓  Untagged steps are labeled "context-only" in the step list.

✓  The author can save a recipe with untagged steps; a warning is shown but it is not blocking.

✓  Untagged steps have their outcome mapping inferred by the AI at session start; the inference is stored in the session record for review.

AUT-06
Upload background documentation
DOMAIN EXPERT
Phase 1 — PoC
Story
As a domain expert, I want to provide reference material so that the AI agent's probing questions and rubric scoring are grounded in the actual content of the module.
Acceptance
✓  The form accepts PDF and DOCX file uploads (max 10 MB per file, max 5 files). Files are stored in S3.

✓  Pasted text is accepted in a dedicated text area (max 10,000 characters).

✓  External URLs can be added with a display label; content is fetched and indexed on save.

✓  Uploaded files are confirmed with filename and size displayed.

✓  A warning is shown if total documentation volume approaches the AI context limit.

AUT-07
Define probing rules and vague answer triggers
DOMAIN EXPERT
Phase 1 — PoC
Story
As a domain expert, I want to specify if/then probing rules so that the agent handles predictable student response patterns in the way I would as an instructor.
Acceptance
✓  Probing rules are entered as trigger / follow-up pairs. Up to 10 rules per recipe.

✓  Vague answer triggers are entered as a list of response pattern descriptions.

✓  Career transfer prompts are entered as a list of 1–3 questions for use toward the end of the conversation.

✓  The form provides example rules as inline guidance.

✓  Rules can be deleted and reordered before saving.

AUT-08
Preview generated check-in questions
DOMAIN EXPERT
Phase 1 — PoC
Story
As a domain expert, I want to preview the check-in questions the AI would generate from my recipe so that I can verify they are appropriate before students see them.
Acceptance
✓  A "Preview check-in questions" button sends the current (unsaved) recipe to the AI and displays the generated questions.

✓  The preview shows the question text and response format for each question.

✓  The preview is clearly labeled as a sample and notes that questions may vary between sessions.

✓  The preview does not require saving the recipe first.

AUT-09
Revise and version a recipe  ★
DOMAIN EXPERT
Phase 1 — PoC
Story
As a domain expert, I want to update an existing recipe in the Admin App and have the previous version preserved so that I can track how the recipe has evolved.
Acceptance
✓  Editing and saving an existing recipe in the Admin App creates a new version and activates it.

✓  The previous version is retained in Aurora and marked inactive.

✓  A version history list shows all versions with their saved timestamp.

✓  An author can view but not edit a previous version.

✓  Rolling back to a previous version creates a new version (copy) rather than overwriting current.

✓  In-progress student sessions continue on the recipe version they started with.

DOMAIN EXPERT
Phase 2 — Pilot
Story
As a domain expert, I want to record observations from real student sessions against a recipe so that the validation log informs future revisions.
Acceptance
✓  A validation log section is available on the recipe detail view after the recipe has been used in at least one session.

✓  Notes can be appended with a timestamp; existing notes cannot be edited or deleted.

✓  Notes are free text with a 1,000 character limit per entry.

✓  The log is visible to the author and instructor roles but not to students.

✓  Instructor disagreement flags from evaluation reviews are surfaced in the validation log.


Instructor stories (INS)
INS-01
View module completion status  ★
INSTRUCTOR
Phase 2 — Pilot
Story
As an instructor, I want to see which sessions have completed the module and what outcome they received in the Admin App so that I can monitor cohort progress.
Acceptance
✓  The Admin App instructor module lists all sessions for a given module with: session ID, completion status, badge awarded, attempt number, and completion timestamp.

✓  No student PII (name, email, Canvas ID) is displayed — identity linkage is done in the Canvas gradebook using the grade return.

✓  The list can be filtered by completion status and sorted by timestamp.

✓  The view is read-only; no session data can be modified from this view.

✓  Only sessions still active in DynamoDB are shown; destroyed sessions are not listed.

INS-02
Review a conversation transcript
INSTRUCTOR
Phase 2 — Pilot
Story
As an instructor, I want to read the transcript of a checkout conversation so that I can understand the quality of student responses and validate the agent's evaluation.
Acceptance
✓  Selecting a completed session displays the full conversation transcript in a readable format.

✓  Agent and student turns are displayed in alternating visual styles.

✓  The rubric evaluation is shown alongside the transcript for reference.

✓  Transcripts are available only for sessions that reached Phase 4 and are still in DynamoDB.

✓  Transcripts are not accessible after the session record has been destroyed on completion.

INS-03
Export session results to CSV  ★
INSTRUCTOR
Phase 2 — Pilot
Story
As an instructor, I want to export a CSV of session results for a module so that I can analyze outcomes in a spreadsheet.
Acceptance
✓  An "Export CSV" button downloads a file with one row per session.

✓  Columns include: session ID, module ID, phase reached, attempt number, rubric dimension ratings, badge awarded, completion timestamp, and grade posted score.

✓  No student PII is included in the export.

✓  The export covers only sessions currently active in DynamoDB; completed and destroyed sessions are not included unless a research export is requested through the researcher module.

✓  The export is available only to users with the instructor role.

INS-04

As an instructor, I want to grant an additional retry attempt to a student who has reached the retry limit so that exceptional circumstances can be accommodated.

✓  The action is logged in the audit log with the instructor role identifier and a required reason field.

✓  The student can then relaunch from Canvas and proceed with the additional attempt.

✓  The retry allowance override does not change the module-level default retry limit for other sessions.

As an instructor, I want to add observations about student performance to the recipe's validation log so that the domain expert can use them to improve the recipe.

INS-06

✓  Review annotations are saved to the session record and surfaced in the recipe validation log.

✓  Disagreement annotations trigger a flag visible to the domain expert when reviewing the recipe.


Researcher stories (RES)
RES-01
Access de-identified research data
RESEARCHER
Phase 3 — Research
Story
As a researcher, I want to query de-identified student interaction data from the Admin App so that I can conduct educational research on learning outcomes and conversation quality without accessing student PII.
Acceptance
✓  The researcher module in the Admin App provides a data browser for the Aurora research schema (research.sessions, research.checkin_responses, research.transcripts, research.evaluations, research.interaction_timing).

✓  Data can be filtered by module ID, cohort ID (module + academic period), date range, badge awarded status, and outcome ratings.

✓  No direct student identifiers are present in any query results — only session-level data linked to cohort IDs.

✓  Access to the researcher module requires the researcher role; it is not available to instructor or author roles.

✓  The research schema is not populated until IRB approval is confirmed; the module displays a clear status indicator of IRB approval state.

RES-02
Export de-identified dataset
RESEARCHER
Phase 3 — Research
Story
As a researcher, I want to export a de-identified dataset for a module so that I can analyze it in external statistical tools.
Acceptance
✓  The researcher can export any combination of the five research tables as a linked CSV or JSON package.

✓  Exports are linked by research session ID (not DynamoDB session ID or any student identifier).

✓  Interaction timing data is exported as relative offsets in seconds from session start, not as wall-clock timestamps.

✓  Transcript content has passed through the de-identification text filter before storage; the researcher sees the filtered version.

✓  All exports are logged in the audit log with the researcher role identifier, module ID, date range, and timestamp.

RES-03
View consent configuration
RESEARCHER
Phase 3 — Research
Story
As a researcher, I want to see which sessions were conducted under which consent configuration so that I can ensure my analysis only includes appropriately consented data.
Acceptance
✓  Each research session record includes a consent_config field indicating the IRB protocol and consent condition under which data was collected.

✓  The researcher can filter query results by consent_config.

✓  Sessions collected before IRB approval are flagged and excluded from research queries by default.

✓  The consent configuration for a module is set by the administrator and cannot be changed retroactively.


Administrator stories (ADM)
ADM-01
Register the platform as a Canvas external tool
ADMINISTRATOR
Phase 2 — Pilot
Story
As a platform administrator, I want to register the Student App as an LTI 1.3 external tool in Canvas so that students can launch activities from their assignments.
Acceptance
✓  Documentation specifies the four required registration values: OIDC login URL, redirect URI, JWKS URL, and target link URI.

✓  A health-check endpoint confirms the LTI service is reachable before registration is attempted.

✓  Registration instructions distinguish dev, staging, and prod URLs clearly.

✓  After registration, a test launch from a Canvas sandbox course confirms the full LTI flow end-to-end including session creation and SAP pool acquisition.

ADM-02
Provision the SAP account pool
ADMINISTRATOR
Phase 2 — Pilot
Story
As a platform administrator, I want to populate the SAP account pool with pre-provisioned sandbox accounts so that students can be assigned a working SAP environment on launch.
Acceptance
✓  A bulk import tool (CSV upload or CLI script) populates the cap-sap-pool DynamoDB table with SAP usernames.

✓  Imported accounts are set to "available" status by default.

✓  A pool status view in the Admin App shows total, available, and in-use counts.

✓  A minimum pool size warning threshold is configurable; an alert is shown when available accounts fall below it.

✓  Accounts can be individually removed from the pool without affecting in-use accounts.

ADM-03
Monitor SAP pool utilization
ADMINISTRATOR
Phase 2 — Pilot
Story
As a platform administrator, I want to see the current state of the SAP account pool so that I can detect exhaustion or stale locks before they affect students.
Acceptance
✓  The pool status view in the Admin App refreshes automatically or on demand.

✓  Accounts in_use for longer than the session TTL are flagged as potentially stale.

✓  An administrator can manually release a stale account after confirming it is safe to do so.

✓  A force-release triggers the SAP account reset before returning the account to available.

ADM-04
Manage application secrets
ADMINISTRATOR
Phase 2 — Pilot
Story
As a platform administrator, I want to store and rotate API keys and credentials in AWS Secrets Manager so that no sensitive values appear in code or configuration files.
Acceptance
✓  All required secrets are documented with their Secrets Manager key names, expected format, and rotation guidance.

✓  The backend retrieves secrets from Secrets Manager at startup; no secrets are read from environment variables in production.

✓  Rotating a secret does not require a redeployment — the backend picks up the new value within one Lambda cold start.

✓  A missing or malformed secret causes a clear startup error with the name of the missing key.

ADM-05
Configure a module  ★
ADMINISTRATOR
Phase 2 — Pilot
Story
As a platform administrator, I want to configure the module-level settings so that SAP verification, content block sequencing, badge issuance, retry limits, and grade mapping are correctly set before students launch.
Acceptance
✓  A module configuration record can be created or updated via the Admin App or a CLI tool.

✓  Required fields: module ID, recipe ID, required SAP document types.

✓  Optional fields: badge template ID, score mapping, retry limit (default 2), SAP verification timeout (default 15s), max session age (default 8h).

✓  The recipe ID links the module to the active instructional recipe in Aurora, including its content block sequence and gate configuration.

✓  Saving a module configuration takes effect for all new sessions launched after the save; in-progress sessions are not affected.

ADM-06
View the audit event log
ADMINISTRATOR
Phase 2 — Pilot
Story
As a platform administrator, I want to query the audit event log in the Admin App so that I can diagnose integration failures and respond to support requests.
Acceptance
✓  The audit log (stored in Aurora) can be queried by session ID, event type, severity, and date range.

✓  ERROR-severity events are surfaced in an admin dashboard without requiring a manual query.

✓  Log entries contain no student PII — only session ID, tempuser ID, and module ID.

✓  Logs are retained for 90 days; a warning is shown as entries approach the retention boundary.

✓  Log entries cannot be edited or deleted by any user role.

ADM-07
Monitor external integration health
ADMINISTRATOR
Phase 2 — Pilot
Story
As a platform administrator, I want to see the health status of each external integration so that I can quickly identify which system is causing failures.
Acceptance
✓  A health dashboard shows the last-known status of Canvas, SAP, Credly, and Anthropic: OK, DEGRADED, or UNREACHABLE.

✓  Status is derived from the most recent audit log entries for each integration.

✓  The dashboard shows the timestamp of the last successful call and the last error for each system.

✓  No active health-check polling is performed — status is inferred from operational traffic.

ADM-08
Manage IRB approval and research schema access  ★
ADMINISTRATOR
Phase 3 — Research
Story
As a platform administrator, I want to manage the IRB approval status and research data collection configuration so that de-identified data is only collected under approved conditions.
Acceptance
✓  The Admin App includes an IRB configuration panel showing the current approval status for each module's research data collection.

✓  The research.* tables in Aurora are not populated for a module until the administrator confirms IRB approval for that module.

✓  The consent_config field for a module is set by the administrator and applied to all sessions collected under that configuration.

✓  Changing the IRB or consent configuration does not retroactively alter existing research records.

✓  The researcher role can only be granted by an administrator; it is not available through self-service.

ADM-09
Handle a FERPA data request  ★
ADMINISTRATOR
Phase 2 — Pilot
Story
As a platform administrator, I want to be able to confirm what student data the platform holds so that I can respond accurately to a FERPA data request or audit.
Acceptance
✓  A maintained data inventory document specifies: what data is held in DynamoDB (ephemeral, TTL-governed, destroyed on completion), what is held in Aurora (de-identified only, no student PII), and what is held in S3 (recipe documentation, no student data).

✓  The Aurora research schema contains no direct student identifiers — only cohort IDs, relative timestamps, and filtered transcript content.

✓  The de-identification process (four steps: strip identifiers, assign cohort ID, relativize timestamps, filter transcript content) is documented and auditable.

✓  Session destruction on completion is logged in the audit log, providing a record that ephemeral data was deleted.

✓  The data inventory document is updated whenever the data model changes and is version-controlled alongside the codebase.
